# Spec：慧景科技數據 PM 面試簡報網站

Label: `ready-for-agent`
詞彙依據：[CONTEXT.md](../CONTEXT.md)

## Problem Statement

講者（陳映安 Alan）要在慧景科技數據產品經理的下一輪面試中，用約 15 分鐘向面試官說明：(1) 實際參與過的專案內容、(2) 數據分析經驗。傳統投影片無法同時做到「豐富互動與視覺」和「證明程式設計基礎能力」；而且面試官會在自己的裝置上同步開啟連結，需要一個雙方容易對齊位置的載體。

## Solution

一個部署於 GitHub Pages 的單頁靜態網站（`https://tpma1205.github.io/interview-presentation/`），採「分節長頁 + 每節滿版」形態：垂直捲動、scroll-snap 停靠、每節有「章-節」編號，固定導覽列顯示目前位置並支援鍵盤與點擊跳轉。內容分兩章共 9 節，無開場與收尾節：

| 編號 | 節 | 主要視覺 |
|---|---|---|
| 1-1 | 專案與平台 | 四泳道流程圖（業者 / 執行團隊 / 政府 / 系統） |
| 1-2 | 團隊組織 | 職能圖（中央團隊 + 四職能 + 上層管理框） |
| 1-3 | 我的角色 | 六張職責卡片全文並列 |
| 2-1 | 逾期繳費｜問題與數據 | 繳費時點圖（1–30 天，雙峰在第 1 / 14 天，逾期 3%） |
| 2-2 | 逾期繳費｜解法與成果 | 模擬 Google Sheet UI + 三步流程 + 前/後切換圖（3% → 0.2%） |
| 2-3 | 逾期申報｜問題 | 「經常」的定義問題 |
| 2-4 | 逾期申報｜方法演進 | 5 家虛構業者三欄排名對照表 + 1–5 星類比 |
| 2-5 | 逾期申報｜貝氏平均模擬 | 公式 + m 說明 + 預覽圖 + 「開啟模擬工具」新分頁按鈕 |
| 2-6 | 逾期申報｜結果 | 與主管討論後採用 |

視覺：白底、慧景 teal `#3F8C92` 為強調色、文字 `#1A1F27`、薄荷 `#8CFFD2` 僅用於極少數高亮數字。

## User Stories

### 導覽與同步
1. As a 面試官, I want 打開連結後第一屏就看到 1-1 與講者身分（導覽列「陳映安 Alan ｜ 數據產品經理 面試簡報」）, so that 不需要開場頁也知道這是誰的簡報。
2. As a 講者, I want 每節有唯一的「章-節」編號並顯示在導覽列, so that 口述時能一句話讓面試官對齊位置。
3. As a 面試官, I want 用滑鼠滾輪捲動時自動停靠在整節, so that 不會停在兩節之間的半截畫面。
4. As a 講者, I want 用 ← → / ↑ ↓ / PageUp / PageDown 鍵切換上下節, so that 現場操作像投影片一樣順手。
5. As a 面試官, I want 點擊導覽列的章或節直接跳轉, so that 可以回頭看前面的內容。
6. As a 面試官, I want 網址帶 `#2-1` 這類 hash 時直接定位到該節, so that 講者可以傳特定節的連結。
7. As a 講者, I want 捲動時導覽列即時更新目前節編號與章名, so that 我和面試官都知道現在在哪。
8. As a 面試官, I want 導覽列上有整體進度指示（例如第 4 / 9 節）, so that 知道還剩多少內容。

### 一目了然
9. As a 面試官, I want 所有文字內容預設可見、不需要點擊展開, so that 快速掃一眼就能掌握每節重點。
10. As a 面試官, I want 每節只有一個主標題與少量重點文字、視覺元素佔主要面積, so that 跟著口述看而不是讀稿。
11. As a 面試官, I want 頁面沒有自動播放動畫或進場特效, so that 我自己裝置上的畫面與講者的畫面一致。

### 專案篇
12. As a 面試官, I want 在 1-1 看到泳道圖上每個步驟落在哪個角色（業者 / 執行團隊 / 政府 / 系統）, so that 立刻理解平台自動化了什麼、人工做什麼。
13. As a 面試官, I want 1-1 泳道圖清楚顯示三審制（一審執行團隊、二審與三審政府）, so that 看出講者團隊在流程中的位置。
14. As a 面試官, I want 1-1 標示繳費的兩種管道（下載繳款單 / 行動支付）與台灣銀行對帳為系統步驟, so that 理解平台的完整閉環。
15. As a 面試官, I want 在 1-2 看到執行團隊為「講者 + 4 位行政客服」且四人共同分攤四項職能, so that 不誤解為各有專責。
16. As a 面試官, I want 1-2 四項職能各標示對應 1-1 的哪個流程步驟, so that 兩節之間有連貫感。
17. As a 面試官, I want 1-2 有一個上層框顯示講者的管理職責（年度方向 / SOP / KPI）, so that 看出講者是團隊主管而非成員。
18. As a 面試官, I want 在 1-3 看到六項職責（專案管理、平台維運、資料庫管理、法律諮詢、宣導會議、管理團隊）並列且各有 2–3 行摘要, so that 一屏掌握講者的完整角色。
19. As a 講者, I want 1-3 的資料庫管理卡片只列職責（清洗、補遺、正規化、分析、報表、議員索資）不放實例, so that 實例留給分析篇講。
20. As a 面試官, I want 1-3 宣導會議卡片顯示「每年 3 場、每場約 200 人、擔任講者」, so that 量化講者的溝通經驗。
21. As a 面試官, I want 1-3 專案管理卡片顯示「評選得標 → 執行合約 → 報告書與審查會議 → 驗收」的完整週期, so that 看出講者有端到端交付經驗。
22. As a 面試官, I want 全站以「前公司」「執行團隊」稱呼而不出現公司名, so that 看出講者對前雇主資訊的謹慎。

### 分析篇：逾期繳費
23. As a 面試官, I want 在 2-1 看到一張橫軸 1–30 天、縱軸案件佔比 % 的繳費時點圖, so that 理解繳費行為的分布。
24. As a 面試官, I want 2-1 圖上第 14 天有一條標「繳費期限」的垂直線、15 天以後底色標示「逾期」, so that 一眼看出雙峰與逾期長尾。
25. As a 面試官, I want 2-1 圖上 hover 任一天顯示該天的佔比, so that 可以自己探索數據。
26. As a 面試官, I want 2-1 用大數字卡顯示「逾期率 3%」, so that 問題規模一目了然。
27. As a 面試官, I want 2-1 有一行小字註明「示意數據，分布形狀依實際觀察」, so that 明白這不是真實案件資料。
28. As a 面試官, I want 2-2 看到一個仿 Google Sheet 的表格（案件編號、開單日、到期日、剩餘天數）且剩餘 ≤ 3 天的列以顏色高亮, so that 理解「即將到期」的判斷機制。
29. As a 面試官, I want 2-2 有三步流程「每日自資料庫匯出 → 條件格式高亮 ≤ 3 天 → 行政人員電話提醒」, so that 理解解法的實際運作。
30. As a 面試官, I want 2-2 有「改善前 / 改善後」切換，圖的逾期區從 3% 縮到 0.2%, so that 直觀看到成果。
31. As a 講者, I want 前/後切換時圖表平滑過渡（Chart.js 內建動畫）, so that 對比更有衝擊力。
32. As a 面試官, I want 2-2 用大數字卡顯示「3% → 0.2%」, so that 成果數字被強調。

### 分析篇：逾期申報
33. As a 面試官, I want 2-3 說明情境（辦宣導會、鎖定「經常逾期申報」的業者）與核心問題（「經常」怎麼定義）, so that 理解為何需要方法論。
34. As a 面試官, I want 2-4 看到固定的 5 家虛構業者（申報件數、逾期件數）, so that 三種方法可以在同一組數據上比較。
35. As a 面試官, I want 2-4 三欄分別顯示「總逾期次數」「算術平均逾期率」「貝氏平均逾期率」的排名, so that 看出每種方法把誰排第一。
36. As a 面試官, I want 2-4 每欄下方一句話說明該方法的缺陷（偏向大戶 / 被小樣本扭曲）, so that 理解方法演進的理由。
37. As a 面試官, I want 2-4 有一行 1–5 星評分系統的類比（1 則 5 星 vs 500 則 4.6 星）, so that 用熟悉的例子理解小樣本問題。
38. As a 面試官, I want 2-5 看到貝氏公式 w = (v·r + m·c) / (v + m) 與五個變數的說明, so that 理解方法本身。
39. As a 面試官, I want 2-5 一句話說明 m（信心常數）的作用, so that 知道調參的意義。
40. As a 面試官, I want 2-5 有模擬工具的靜態預覽圖與「開啟模擬工具 ↗」按鈕，點擊在新分頁開啟 NTPC_SimBayes, so that 想深入時可以親自操作。
41. As a 講者, I want 2-5 即使面試官不點按鈕也能一目了然, so that 互動是加分而非必要。
42. As a 面試官, I want 2-6 看到結論（與主管討論後採用貝氏平均法）與這個決策的意義, so that 知道分析真的影響了決策。

### 裝置與部署
43. As a 面試官, I want 在 ≥ 1024px 的筆電/會議室螢幕上版面最佳化, so that 現場觀看清楚。
44. As a 面試官, I want 用手機開啟時內容可讀、不破版（節改為至少一屏高、卡片單欄、泳道圖可橫向捲動）, so that 事後隨手點開也能看。
45. As a 講者, I want push 到 `main` 後 GitHub Pages 直接上線、不需要 build, so that 修改後幾分鐘內就能重新分享。
46. As a 面試官, I want 打開 repo 時 README 說明專案目的與結構、CONTEXT.md 說明詞彙, so that 看出講者有文件化的習慣。
47. As a 面試官, I want repo 的程式碼結構清楚（HTML / CSS / JS / data 分離）, so that 30 秒內看懂講者的程式能力。
48. As a 講者, I want 頁面 `<title>` 為「陳映安 Alan ｜ 數據產品經理 面試簡報」, so that 瀏覽器分頁與分享預覽顯示正確。

## Implementation Decisions

- **技術棧**：純 HTML / CSS / JavaScript，Chart.js 經 CDN 載入，無框架、無建置流程。理由：9 節靜態內容 + 少量圖表，框架是過度設計；vanilla 更能讓面試官快速讀懂。
- **頁面形態**：單一 HTML 文件，每節為一個 `<section>`，容器使用 CSS scroll-snap（`y mandatory`）；桌機每節 `height: 100vh`，手機（< 1024px）改為 `min-height: 100vh` 並允許節內捲動。
- **導覽列**：固定於頂部，左側身分文字，右側兩章（專案篇 / 分析篇）及節編號清單；以 IntersectionObserver 追蹤目前節並同步更新 URL hash。鍵盤事件處理 ←→↑↓ / PageUp / PageDown 切換上下節。
- **一目了然原則**：禁止 tab、手風琴、點擊展開、進場動畫。唯一允許的互動：圖表 hover、2-2 前/後切換、2-5 外連按鈕。
- **視覺系統**：白底；強調色 teal `#3F8C92`（亮版 `#5BACB1`）；文字 `#1A1F27` / 次要 `#2B323D`；薄荷 `#8CFFD2` 只用於「0.2%」等極少數高亮；無襯線字體、圓角卡片；所有顏色定義為 CSS 變數。
- **模擬數據**：全部由程式生成或寫死，不含真實業者資料。
  - 繳費時點分布：1–30 天，寫死一組佔比陣列；第 1 天與第 14 天為兩個峰值；15–30 天合計 3%（改善前）與 0.2%（改善後）；兩組陣列各自總和為 100%。
  - 2-4 五家業者：寫死申報件數與逾期件數，並手工驗證三種排名各自把不同業者排第一（總次數→大戶、算術平均→小樣本、貝氏平均→真正高逾期率且樣本足夠者）。
  - 2-2 表單：寫死約 8–10 列假案件，其中 2–3 列剩餘天數 ≤ 3。
- **純函數模組**：貝氏平均計算、三種排名、分布陣列的正規化/驗證抽成無 DOM 依賴的 ES module，供頁面與測試共用。
- **泳道圖與職能圖**：手刻 inline SVG，四泳道（業者 / 執行團隊 / 政府 / 系統），步驟：申報 → 一審 → 二審 → 三審 → 開立繳款單 → 繳費（下載 / 行動支付）→ 台銀對帳 → 開放憑證。靜態、無動畫。
- **2-5 外連**：`<a target="_blank" rel="noopener">` 指向 `https://tpma1205.github.io/NTPC_SimBayes/`；預覽圖為該工具的靜態截圖放在 assets。
- **身分與匿名**：導覽列與 `<title>` 顯示「陳映安 Alan ｜ 數據產品經理 面試簡報」；全站不出現前公司名稱。
- **部署**：推至 `main`，GitHub Pages 設定為 Deploy from branch → `main` → `/ (root)`；加入 `.nojekyll`。Pages 啟用需講者在 GitHub 網頁介面操作一次（環境無 `gh` CLI）。
- **Repo 內容**：`index.html`、`style.css`、`app.js`、純函數模組、`data/`、`assets/`、`README.md`、`CONTEXT.md`、`docs/SPEC.md`、`.nojekyll`。

## Testing Decisions

- **好的測試**：只驗證外部行為——給定輸入陣列，排名結果與貝氏數值正確；不測 DOM 結構或 Chart.js 內部。
- **測試接縫（seam）**：唯一的自動化接縫是純函數模組（貝氏平均、三種排名、分布陣列驗證），用 Node 24 內建 `node:test` 執行，零依賴。具體案例：
  - 貝氏平均：v=0 時 w=c；m=0 時 w=r；固定五家業者的 w 值與手算一致。
  - 排名：五家業者在三種方法下第一名各不相同，且符合設計意圖。
  - 分布：改善前/後兩組陣列總和為 100%（容差 0.01）、15–30 天合計分別為 3% 與 0.2%、峰值位於第 1 與第 14 天。
- **人工驗證清單**（無自動化）：在瀏覽器（桌機 1440px、手機 375px）逐節檢查捲動停靠、鍵盤切換、hash 跳轉、導覽同步、前/後切換、外連新分頁、無破版。
- **無既有測試先例**：本 repo 從零開始；NTPC_SimBayes 亦無測試。

## Out of Scope

- 開場節與收尾節（講者決定不需要）。
- 任何點擊展開、tab、手風琴等隱藏內容的元件。
- 手機端的專門排版美化（僅要求可讀、不破版）。
- 前端框架、建置工具、GitHub Actions。
- 內嵌（iframe）NTPC_SimBayes；重寫或改版該工具。
- 真實案件資料、真實業者名稱、前公司名稱。
- 「為何不自動化每日匯出」的說明（講者選擇現場口頭回答）。
- 1-3 資料庫管理的具體實例（留給分析篇）。
- 講者講稿 / 演講備註。
